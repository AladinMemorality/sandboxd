# Twelve-app workload acceptance did not pass

All twelve synthetic2 CPU/2 GiB apps became ready, but the corrected workload
failed its20-second full-residency deadline. Each app targeted512 MiB of touched
memory. At the last fully successful polling round, process RSS was157–165 MiB;
three final responses reached165–169 MiB before the shared preparation deadline.
No app reported the full resident allocation, and no45-second steady workload
interval was measured. The earlier allocation-only burst result cannot establish
twelve busy applications are production-ready.

The asynchronous start acknowledgments all succeeded within230 ms. During memory
preparation, twelve complete polling rounds returned app and supervisor responses;
the slowest successful HTTP response was2.329 seconds. The final preparation
context expired and canceled outstanding reads. HTTP deadlines remained5 seconds.
The previous synchronous version had failed an initial5-second-bounded `/start`
request; that failure is retained rather than replaced with the new result.

All twelve guests were deleted. Durable charged reservations were zero, and an
independent authenticated API inventory plus `cubemastercli list --all --wide`
both confirmed zero guests. There were no worker/outer global OOM increments or
QEMU cgroup `oom`, `oom_kill` or `max` events. The outer QEMU cgroup's peak sampled
memory during the final86.68-second fixture was17.151 GiB. This is the entire
worker VM cgroup footprint, not the synthetic application memory total.

## What the recorded counters establish

Over the whole final fixture, the outer QEMU cgroup consumed304.281 CPU-seconds:
237.617 system and66.665 user. Its throttled-period count rose by216, and
`throttled_usec` rose by35.908 seconds. This is an aggregate cgroup counter;
it does not mean the entire host stopped for35.908 wall-clock seconds.
The reviewed worker unit provides12 vCPUs under outer `CPUQuota=1000%`, while
twelve2-vCPU apps expose24 guest vCPUs. The memory-touch phase can consume much
more CPU than the later5%-of-one-core compute loop. It is therefore credible
that simultaneous memory faults hit the host CPU ceiling. No quota was changed.

The local pinned Cube source provides another relevant mechanism:

- `Cubelet/storage/local.go`, `prefetchRestoreMemoryVolURL`, documents that XFS
  template/resume restoration maps the original snapshot memory `MAP_PRIVATE`.
- `Cubelet/storage/cow/store.go`, `CloneSandboxMemory`, distinguishes this XFS
  mapping from the separate memory clone used by same-node S3 pause/resume.
- `CubeShim/shim/src/sandbox/sb.rs` passes the resolved `memory_vol_url` into
  `RestoreConfig`; the workload used the reviewed XFS template path.

These were inspected in the existing local copy of pinned upstream31d911e with
separate reviewed recovery patches; no active worker probing was performed
while the crash fixture held the worker. Private snapshot mappings can defer
copy-on-write/page-fault work until application writes. Combining that mechanism
with nested virtualization and the observed kernel CPU cost is a plausible
explanation for slow first touch. **The counters do not isolate COW, nested page
faults, CPU quota or memory-backend costs as the root cause.** Per-process fault
counts and phase-aligned CPU samples were not captured in this run, so claiming
one cause would overstate the evidence.
