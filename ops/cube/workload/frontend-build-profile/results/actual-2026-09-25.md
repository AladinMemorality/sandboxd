## Resource interpretation

`resource-phases-2026-09-25.json` uses the original guest report's integer
`wall_time_ns` markers. JavaScript reserialization rounds these large numbers, so
the journal's embedded report was deliberately not used for time boundaries.
The analyzer retains actual sample coverage and missing edges; it does not
interpolate short phases or infer build activity from the prior AI task.

During the build, eight VM process samples covered 7.006 seconds of the 8.314
second marker interval: **11.21 CPU-seconds**, averaging **160.0% of one core**.
There was only **one** five-second-cadence guest-container memory observation
inside this interval: **842.47 MiB**. Thus no guest-container CPU delta can be
reported for the build alone. Guest VM PSS peaked at **1,230.10 MiB** during the
sampled build. The entire copy/start/build/API/cleanup envelope had eight guest
memory observations and 39 VM observations: guest memory sampled peak
**842.47 MiB**, VM PSS peak **1,231.16 MiB**.

VM cgroup charge reached approximately **1,890 MiB**, with approximately
**1,002 MiB** reported in its file/cache component. These are overlapping memory
views and must not be added to the guest's memory figure or the whole worker's
QEMU memory. This measurement does **not** justify reducing guests to 1 GiB.
Sampled guest-VM and whole-worker cgroup OOM and throttling counters did not
increase during the workload; observed swap remained zero. The child process
RSS value in the build report (242,572 KiB) is Linux `RUSAGE_CHILDREN` cumulative
high-water RSS, not total guest or simultaneous process-tree RAM.

Very short HMR and cleanup phases had fewer than two resource samples and
therefore have no fabricated CPU/counter delta. The sampler's before/after
intervals include supervisor reloads and later operator activity; they are not
clean idle baselines. The whole-worker view also includes services, observer
overhead and other activity, and cannot be attributed entirely to this guest.
