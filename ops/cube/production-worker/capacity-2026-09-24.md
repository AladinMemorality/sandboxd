# Capacity decision and applied limits

The initial worker was24GiB /6vCPU; it is now40GiB /12vCPU under the selected
policy below. The initial measurements are historical observations, not a
claim that61 projects or all currently running projects fit at once. Preserve
the observed **two-CPU /2GiB** per-project limits. A later read-only Docker sample
found28 running guests using about4.72GiB total at that instant and about5.96%
summed CPU. The benchmark QEMU RSS was12.06GiB; the new VM while compiling was
7.72GiB; outer available RAM was about37GiB. Idle RSS is not a reserved-memory
or future peak bound. The earlier24-running observation was already stale.

Pinned upstream source31d911e confirms:

- `Cubelet/pkg/cubelet/node_status.go`: fallback CPU quota is2×logical CPU and
  memory quota is5/4 of detected RAM. Set explicit positive quotas instead of
  relying on those fallback values or registration defaults.
- `Cubelet/dynamicconf/conf.yaml`: `paused_resource_release_ratio` defaults0;
  paused guests retain their full quota. Full fleet storage requires releasing
  paused reservations; ratio1 is the straightforward option, with controlled
  resume admission and honest capacity rejection.
- `Cubelet/services/cubebox/update.go`: resume checks are optimistic; concurrent
  resumes can each pass against an unchanged allocation snapshot. Create
  scheduling is also optimistic. `creation_concurrent_num: 1` alone does not
  serialize all resumes, preview auto-wakes and snapshot-clone paths.
- The resource accounting uses `ResourceWithOverHead`, including0.3 host CPU per
  two-CPU guest,16MiB message memory,42MiB VM base,64/63 memory scaling and20MiB
  host base. Without a larger matched snapshot specification, a2GiB container
  therefore consumes approximately2160MiB host quota. Inspect the actual
  registered template/guest accounting; a larger matched snapshot size changes
  the result. Do not calculate admission using2048MiB alone.

An explicit24,000m CPU quota on a12vCPU worker permits only about10 guests at
2,300m accounted each. Increasing CPU overcommit to accommodate16–18 guests
needs an intentional workload policy and measured simultaneous-build latency;
it preserves each guest's ceiling but does not deliver dedicated CPU capacity.
Outer systemd memory limits must also be resized deliberately.48GiB guest RAM
plus VMM overhead leaves considerably less reserve on a62GiB shared host than
40GiB. Retained Docker workloads, database/platform/capture peaks and unrelated
services all need room. Do not rely on swap as guest capacity.

For61 paused projects, memory snapshot files alone have122GiB nominal logical
size at2GiB each; with the ordinary2140MiB VM calculation it is approximately
127.5GiB, before image/template layers, writable home/database data, previous
snapshots, build caches and backup staging. Do not assume compression or sparse
storage makes the worst case disappear. The altered benchmark currently uses
about69GiB under `/data/CubeMaster`; that is an observation, not a fresh-template
storage measurement. The240GiB data disk leaves little expansion margin once
full fleet data and snapshots are counted. A fresh384GiB data disk is a possible
later expansion within the observed512GiB NVMe free space, but has not been
authorized/applied and still needs explicit growth/retention/backup budgets.
Per-project10GiB writable quotas sum to610GiB across61 projects: thin provisioned
storage requires aggregate admission/free-space protection, not a claim that
every quota can be simultaneously filled on240GiB or384GiB.

Before owner migration, enforce admission across **every** controller create/
connect/preview wake/clone/restore path, and prevent alternate CubeProxy or direct
API access from bypassing it. A per-sandbox mutex does not serialize cross-guest
admission. After a control-plane crash, rebuild reservations from authoritative
running/creating state before reopening admission. Keep paused guests durable,
return a clear retriable capacity response or queue when full, and test bursts
against the final deployment. Do not inflate quotas to61×2GiB to suppress errors.

The historical analysis above preceded the separately authorized benchmark
retirement and fresh-VM resize, now completed and evidenced alongside this file.
Tenant admission and production routing remain separate acceptance gates.

## Selected policy after user decision

The user selected this VPS with tested limits. The benchmark VM is retired only
after its sole paused guest's persistent artifacts and consistent recovery
metadata are verified and backed up. Its disks remain intact. The fresh worker
is resized to40GiB/12vCPU, with outer MemoryHigh42G, MemoryMax44G and CPUQuota1000%.
Explicit Cube quota is30GiB and28000mCPU. Controller admission must cap the sum of
running, waking and creating at12; paused reservations may be released only with
that controller gate. This is an intentional CPU overcommit policy requiring
burst/build workload tests, not permission to admit all61 simultaneously.

Pinned disk-accounting inspection: metric.go retains paused HostDataDiskMB and
HostStorageDiskMB, but Master scheduler/diskfilter.go gates heartbeat-cached
filesystem-fill percentages, not total logical guest-disk reservations. XFS
CollectDiskUsage uses statfs on/data/cubelet and/data/cubelet/storage. Therefore
61×10GiB logical allowance does not itself create a ~20-guest scheduler ceiling.
It also does not guarantee those610GiB can be written on240GiB. The approved
policy needs an additional synchronous authoritative free-space check reserving
at least48GiB before allocation/import; a cached percentage alone is insufficient.
No disk quota inflation or reduction in the10GiB per-project allowance occurred.
